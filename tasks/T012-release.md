# T012. Регрессия, упрощение и release build

> **User-directed revision, 2026-08-14.** После исходного завершения T012
> пользователь расширил текущий финальный этап десятью конкретными gameplay/UI
> правками. Они реализуются и проверяются в рамках повторного release gate без
> запуска новой задачи из `tasks/manifest.json`; исходный раздел «Не входит»
> не ограничивает это явное последующее поручение.

**Feature spec:** `features/F012-release.md`  
**Зависит от:** T011

## Цель

Провести полный аудит требований, удалить случайную сложность и получить воспроизводимую Docker-сборку.

## Контекст задачи

Открыть только перечисленные файлы и уже созданный код, непосредственно связанный с задачей:

- `features/F012-release.md`
- `quality/DEFINITION_OF_DONE.md`
- `quality/TEST_STRATEGY.md`
- `quality/REVIEW_CHECKLIST.md`
- `quality/CONTEXT_BUDGET.md`
- `quality/ACCEPTANCE.md`
- `specs/technical/11-performance.md`
- `specs/technical/12-documentation.md`
- `specs/technical/13-module-boundaries.md`

Не читать весь пакет «на всякий случай». Если нужное правило отсутствует, применить порядок приоритетов из `README.md`.

## В scope

- полный Docker quality gate;
- E2E ключевых сценариев;
- визуальный аудит по референсам;
- dependency/license audit;
- проверка границ импортов;
- обновление README/CODEMAP;
- трёхпроходное ревью;

## Ожидаемые результаты

- `готовая production image`;
- `README.md и docs/CODEMAP.md`;
- `reports/T012.md`;
- `финальный traceability report`;
- `Playwright traces/screenshots только при ошибках`;

Конкретные имена внутренних файлов можно скорректировать, если сохраняются границы ответственности и это объяснено в отчёте.

## Критерии приёмки

- [ ] все критерии `quality/ACCEPTANCE.md` отмечены доказательствами;
- [ ] lint, format, typecheck, unit, content, build, e2e проходят;
- [ ] нет запрещённых зависимостей и модулей;
- [ ] нет логики баланса в коде;
- [ ] production image запускается одной командой;
- [ ] реализация соответствует scope, без скрытых незаконченных функций;

## Не входит

- новые функции;
- редизайн;
- обновление стека без необходимости;

## Обязательный рабочий цикл

1. До изменений записать план максимум из 8 пунктов.
2. Найти самый маленький законченный вертикальный срез задачи.
3. Сначала добавить/уточнить проверяемые тесты или валидаторы требования.
4. Реализовать минимальный код, необходимый для прохождения этих проверок.
5. Запустить команды через Docker из `quality/THREE_PASS_WORKFLOW.md`.
6. Просмотреть итоговый diff и удалить код, не нужный этой задаче.
7. Создать `reports/T012.md` по `quality/REPORT_TEMPLATE.md`.

## Запрет завершения

Задача не считается выполненной по фразе «должно работать». В отчёте нужны фактические команды, их результат и ссылки на тесты, доказывающие каждый критерий.
