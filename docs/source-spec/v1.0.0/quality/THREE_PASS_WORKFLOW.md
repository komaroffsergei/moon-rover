# Три обязательных прохода после реализации

Цель — получить лучший результат несколькими проверками, не переписывая исправный код ради эстетического беспокойства агента.

## Проход 1. Соответствие спецификации

1. Для каждого критерия задачи указать тест/валидатор, который его доказывает.
2. Запустить целевые unit/integration/content проверки.
3. Исправить только фактические расхождения.
4. Не расширять scope, даже если замечена «интересная возможность».

Результат: таблица `requirement → evidence` в отчёте.

## Проход 2. Простота и границы

Просмотреть diff как независимый ревьюер:

- нет ли правил в React/Phaser;
- нет ли коэффициентов в коде;
- нет ли новой зависимости без необходимости;
- можно ли удалить слой, класс, интерфейс или преобразование без потери поведения;
- не созданы ли абстракции для одного вызова;
- понятны ли имена и единицы;
- нет ли изменения вне задачи.

Исправлять только найденные дефекты. Не проводить «генеральный рефакторинг» соседнего кода.

## Проход 3. Регрессия и пользовательский сценарий

1. Запустить полный доступный quality gate через Docker.
2. Для UI пройти минимум один реальный сценарий мышью через Playwright.
3. Проверить console errors, failed network requests и layout 1280×720.
4. Просмотреть итоговый diff ещё раз.
5. Сверить изменённую документацию и CODEMAP.

## Правило остановки

Если после третьего прохода проверки зелёные и не найдено доказанного расхождения, остановиться. Не начинать четвёртый рефакторинг, потому что модель внезапно вспомнила ещё один паттерн проектирования.
