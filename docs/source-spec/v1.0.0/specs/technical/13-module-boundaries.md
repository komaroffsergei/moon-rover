# Границы модулей и импортов

Цель — не «слоистая архитектура» ради диаграммы, а отсутствие скрытой игровой логики в UI и рендерере.

## Разрешённое направление

```text
shared        → внешние стандартные API без project imports
domain        → shared
content       → domain, shared
simulation    → domain, shared
game          → domain, shared, Phaser
ui            → domain, shared, React, Zustand
app           → content, simulation, game, ui, domain, shared
```

`tests` могут импортировать проверяемый модуль и fixtures. Production-модуль не импортирует тесты.

## Жёсткие запреты

- `domain`, `content` и `simulation` не импортируют `app`, `game`, `ui`, React, Phaser, Zustand или DOM.
- `simulation` не читает файлы контента: она получает уже валидированный `RuntimeContent` через конструктор/функцию создания.
- `game` и `ui` не импортируют внутренние файлы `simulation`; они общаются через публичный controller/commands/snapshot.
- `game` не импортирует `ui`, `ui` не импортирует `game`. Их связывает только `app`.
- `shared` не становится складом доменных типов. Если тип описывает центр, ровер, маршрут или событие, он принадлежит `domain`.
- Циклические импорты запрещены.

## Проверка без новой зависимости

В T001 настроить folder-specific overrides ESLint с core-правилом `no-restricted-imports`. Отдельный dependency-cruiser не добавлять. В T012 просмотреть импорт-граф и выполнить отрицательный fixture/test конфигурации, если ESLint позволяет нарушение незаметно.

## Публичные точки входа

Один `index.ts` допустим только на внешней границе крупной зоны (`domain`, `simulation`, `content`). Не создавать barrel в каждой папке. Внутренние импорты используют прямые пути.

## Критерий простоты

Новый слой разрешён только если:

1. есть минимум два реальных потребителя;
2. он удаляет дублирование поведения, а не только переименовывает вызов;
3. его граница проверяется тестом или ESLint;
4. решение записано в отчёте текущей задачи.
